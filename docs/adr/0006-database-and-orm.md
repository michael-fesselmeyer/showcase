# ADR 0006: Database and data access

- Status: accepted
- Date: 2026-11-15

## Context

The site has had no database: content is typed configuration ([ADR 0001](0001-stack-and-rendering.md)).
The studio tools store relational data (leads, engagements, a ledger) where correctness matters
more than scale: one user, a few thousand rows a year. The service must be free, and the schema
will be public.

## Decision

- **Postgres, hosted on Neon's free plan** in production.
- **Drizzle ORM** for schema definitions and queries, with **SQL migrations generated by
  `drizzle-kit` and committed** under `drizzle/`. Migrations are applied by a deliberate step, not
  automatically on deploy.
- **Rules are enforced in the database** as well as in code: foreign keys, not-null and check
  constraints, unique indexes, and triggers for append-only tables and balanced journal entries.
- **The standard `pg` driver** against Neon's pooled connection string, with a separate direct
  connection for migrations.
- **Tests run against PGlite**, a real Postgres engine running in-process, with the migrations
  applied fresh for each test file. Local development uses a local Postgres database, one per
  working copy.
- **Only the data access layer imports the database client** (see the
  [architecture](../studio-tools/architecture.md)).
- **One schema change is in review at a time.**

## Alternatives considered

- **SQLite (for example Turso):** simple and free, but weaker constraint and trigger support than
  Postgres, and the ledger leans on both.
- **Prisma:** a mature toolkit, but a heavier client and its own schema language; Drizzle's
  schema is TypeScript and its queries read like the SQL they produce, which makes reviewing a
  query for its authorisation filter easier.
- **Hand-written SQL only:** maximum control, no type safety between the schema and the code.
- **A backend-as-a-service (for example Supabase) with its client library and row-level security
  from the browser:** moves authorisation into database policies called directly from the client.
  Powerful, but it makes the database a public API, which is the opposite of the single guarded
  entry point this design wants.
- **Neon's HTTP driver:** fast for single queries from serverless functions, but ledger postings
  need interactive transactions. Revisit if connection time on a cold start becomes noticeable.
- **Mocks instead of a real database in tests:** fast, but the constraints and triggers are part
  of the behaviour under test.

## Consequences

- The schema and its history are public. That is acceptable: nothing about the design relies on
  them being secret.
- The free plan sleeps after five idle minutes, so the first private request after a pause waits
  for the database to wake. Public pages never touch it.
- The free plan's restore history is a few hours, so the application takes its own backups
  ([security model](../studio-tools/security.md)).
- Free-plan limits are recorded in [hosting and free tiers](../studio-tools/hosting-and-limits.md).
- CI gains a check that the schema and the migrations agree.
